# Vulnerability Report Writing Format (Permanent · Sole Authority)

> **2026-08-19:** Report rules consist of these two sections only.
> **Going forward, change report rules only in these two tables in this file.** Additions, removals, and edits belong here; do not put them in Agents, src-value, dig-scope, or other files.

For details on vulnerability types, see `src-value-hunting.md`; **this file alone governs whether to write a report, how to write it, and where to save it.**

---

## I. How to Write the Report (Layout + 8 Blocks)

Describe what I accomplished in plain first-person language. The impact section states only the harm that can ultimately be caused (cover the full permission scope; give examples when available; do not invent examples for things not tested), not the steps. No tutorials. Write for security reviewers.

| Block | Rules |
|-------|-------|
| Vulnerability title | One line. Identify whose site it is and what was accomplished. “Anonymous” means the issue was successfully exploited with no authenticated session; it does not mean it worked with `omit`. Use “anonymous unauthorized” only when there was no authenticated session; never use “not logged in” as a substitute for “unauthorized.” If a session was present, do not say “anonymous” or “anonymous unauthorized”; call access to another person’s object “authorization bypass.” No session + another person’s data → include both “anonymous unauthorized” and “another person’s”; do not say “authorization bypass.” Session + another person’s data → say “authorization bypass,” optionally specifying “another person’s.” For bulk access, include “arbitrary” or “bulk.” See the anonymous gate for details. |
| Target website URL | `Target website URL: https://…` The site a person opens. |
| Severity | Use only Medium, High, or Critical. First establish unauthorized access or an authorization bypass. **Critical** (at least one): a command executed; another person’s account was accessed or their password/binding was changed (a real session obtained by logging into a human account is Critical, not High); money was actually transferred, or a status such as hiring, insurance claims, or approval was actually changed. **High** (not Critical, at least one): data identifies a person (phone, national ID, card, ID photo); cloud key/token/database connection string/session usable as another person (must pass the key-validation gate: production accepts it in a fake-value comparison, and the validation request returns an identity or list; it has not yet been used to log in or transfer money. For DSN/Redis/components, connecting and querying an identity or list is sufficient; this does not mean a human account used to log in to a backend); injection returned another principal’s data; another person’s unpublished business content (such as internal knowledge-base content, an unreleased/unpublished detail page, or ticket body, and specifically body text rather than a title or summary). Accessing another user’s personal-space journal/posts/albums past the permission boundary but seeing only titles or summaries → Medium. Assign severity only when one of these criteria is met; do not jump a level just because one more field was exposed than in a previous report. **Medium**: expanded permissions or business-sensitive impact, while neither High criterion above is met. If unsure, do not write it. |
| Vulnerability description | Put `Vulnerability description:` on its own line, then start the text on the next line. Use plain first-person language with “I” to say what I accomplished (no session: what I accomplished without logging in; session present: how I used my own session to access someone else’s object). With a session, do not write “I was not logged in”; without a session, do not write “I used my own session.” Avoid manual-like phrasing (“This endpoint can be called without authentication”) and do not say “the attacker.” For a successful no-session issue, put “anonymous unauthorized” only in the title; in the description state the fact as “I was not logged in,” do not use “not logged in” as the issue type, and do not begin with “Anonymous unauthorized.” Explain the chain in plain language, but do not copy the endpoint list into the description (full URLs belong in the affected-endpoint list). Do not paste requests, reproduction steps, or an impact list (impact belongs in the impact section). If a hard-coded value/credential/key came from JS, include its full literal value and the complete JS URL (full http(s) path, not just the filename) in the description; citing it in the endpoint list does not replace this requirement. Use line breaks; do not run the body together on one line. |
| Vulnerability impact | Put `Vulnerability impact:` on its own line, then start the text on the next line. State only the ultimate harm that can be caused. Cover the real permissions and data scope of the door opened and the identity/key/data obtained (check menus, role descriptions, write endpoints already tested, and what this key can actually access; do not guess). Judge impact by the access granted, not by how many requests were needed to demonstrate it. Two routine requests for a credential issue are examples for reproduction, not the limit of impact; describe the full scope of that identity. Entering an admin console proves viewing access, but the impact should still describe what can be changed or deleted. If an admin key can retrieve bills, issue refunds, or transfer money, include those capabilities; you do not need to actually refund a transaction. Do not claim access that was not established (if you only saw a role name, do not claim prices can be changed; if changing a password worked but token replacement failed, do not claim “account takeover”—clarify the boundary in the description using “I”). This is not a procedure: do not say “first layer,” “second layer,” “POST as the user,” “change a parameter,” or “full request.” Put each kind of harm on a separate line and plainly name what is affected (people, accounts, money, internal content, ability to modify/delete). Include examples when available: for exposed data, give one or two actual names/phone numbers/addresses/IDs or internal titles; for a proven change, say what it was changed to. For permission scopes not actually exercised (such as ability to delete or refund), state the capability as impact but do not invent “deleted X” or “refunded Y.” If bulk access is possible, say “can disclose/modify in bulk”; do not explain enumeration. Avoid vague wording such as “not limited to” or “other sensitive information”; do not merely say “personal information was exposed” without examples. |
| Affected endpoint list | List only endpoints actually used in the reproduction steps, numbered 1, 2, 3. Give each full URL and its source; if taken from JS, include the full JS URL; if taken from a page, include the page URL. Cite JS used to obtain parameters on the corresponding endpoint; do not list the JS or homepage as a separate endpoint. Do not list comparison endpoints or endpoints that were not tested. |
| Reproduction steps | Number steps 1, 2, 3; include only requests necessary to demonstrate the issue, so a reviewer can follow them. One complete request per step. A request used only to copy a parameter, compare behavior, or see what a page looks like is not a step. Still include a step when evidence appears on the page itself (identity page returns 200, XSS reflection). In the description for the step where a parameter is used, say which JS file or field from the previous step it came from and include its full JS URL or endpoint URL. Put before/after or original-site comparisons in that step’s description; do not create another step and request for them. No need to explain the source of a purely numeric value that can be enumerated. Explain in one or two sentences per step what was sent and what it proves. Do not repeatedly say “without logging in” or “without a Cookie.” Do not describe or paste responses. Never append a response or “expected result” after a request. If a later step needs a decrypted/signed value, give it a separate step: state how to generate it, what it yielded, and how the next step uses it. For credentials/keys/private keys/accounts used to log in, do not write the report until the key-validation gate passes. The first step validates the key or logs in (describe the fake-value comparison in that step; this request must already return an identity or list). Normally make one more read-only request (if the first already returned a result, use a different kind of read). If another request would affect production, submit even a single request as the report (it must still have returned an identity or list). Do not use a refund, modifying someone else’s data, or transferring money as a contrived example. |
| Complete request (in steps) | Include one copyable complete request per step. Put `Host` immediately below the request line. Include `Accept`, `Accept-Language: zh-CN`, `Accept-Encoding: gzip, deflate`, `User-Agent: Mozilla/4.0 (compatible; MSIE 7.0; Windows NT 10.0; WOW64; Trident/7.0; .NET4.0C; .NET4.0E; Tablet PC 2.0)`, and `Connection: close`. If there is a body, also include `Content-Type`, `Content-Length`, and `Cache-Control: no-cache`. Include `Origin` and `Referer` if present on the page. Do not include `Cookie` when the issue worked without a session; when reproducing with a session, include the full literal Cookie value. Never test with a session and then remove the Cookie in the report and label it anonymous. End the request directly with a full-width `＃`. Do not write “expected”; do not describe or paste responses in the steps. |
| Remediation | Give a concise, direct, precise, and actionable fix tailored to the specific vulnerability. |
| Formatting | Put the vulnerability title, target website URL, and severity on three consecutive lines with no blank lines or `＃` separators. Put `Vulnerability description:` and `Vulnerability impact:` on their own lines, with the body starting below each label. Put every kind of impact on its own line; do not use “first layer/second layer.” Separate major blocks with a line containing a full-width `＃`; never use ASCII `#` as the separator. Break each reproduction step onto its own line and put one `＃` line between steps. After reproduction, put one `＃` line, then remediation. No extra blank lines. |
| Saved report file | Save under `Desktop\{任务}_SRC挖洞\报告\`. The filename is the vulnerability-title line, with `.md` extension. Do not leave reports loose in the Desktop root. Use CRLF. Do not put dig material in the report body. If there is no issue to report, do not create an empty report. |

## II. Whether to Report and Where to Save It

| Rule | Details |
|------|---------|
| Do not report | Incomplete chains. Weak passwords without account access. Credential-free configuration shells (including DSNs without credentials, health/version endpoints, or a host with no password). Credentials/keys/private keys that did not pass the “key validation gate” (only copied a string, no fake-value comparison, or validation request returned no identity/list) → do not report. Logging in without a read-only example that returns an identity or list → do not report. Placeholder/expired values or fake and real values producing the same error → do not report. Phone-number encryption/decryption keys (frontend AES/SM4/RSA, salt/iv/key for encrypting phone numbers, or PoC ciphertext that can be decrypted) → do not report. Unauthorized upload/download alone. Low severity, informational issues, configuration reminders, expired certificates (without an exploit chain), missing security headers. CORS. Unauthorized SMS/email/verification-code sending. CAPTCHA or unlimited password attempts without a successful login. Data readable as part of normal duties or within the account’s permissions, public operational data, fingerprints, temporary OSS image links, public documentation. CSRF that affects only yourself. An endpoint returning HTTP 200 with JSON. If unsure, do not report. Do not tell the user “I found a low-severity issue.” If a code-sending/CAPTCHA/file channel leads to account access, password change, or an executable chain, report that resulting issue; do not make a separate report just for “code sending” or “upload.” |
| Report immediately | For confirmed Medium, High, or Critical issues, write them to `报告/` immediately; do not batch reports until the end. An issue is not confirmed for reporting until it passes the anonymous gate and key-validation gate; do not save it before then. |
| Anonymous gate | Before putting “anonymous” in the title, ask: did the request that succeeded include a Cookie, and was the research session logged in? If there was a session → do not call it anonymous; call it an authorization bypass, describe “I used my own session,” and include the full literal Cookie value. Success with `omit` does not count as unauthenticated. |
| Key-validation gate | **Finding a key is not a vulnerability; write it only after production accepts it.** Private keys / PEM / SSH / AKSK / tokens / connection strings / JWTs / sessions usable as another person must pass the gate before reporting. Passing = production accepts the real value in a fake-value comparison, and the validation request returns an identity or list (SSH: fake key gives `Permission denied`, real key gives `Hello username`). Otherwise do not report. Submitting a copied string alone is prohibited. If the first validation request already returned an identity, make one more read-only request of a different kind that does not affect production; if another request would affect production, report the one request (it must still have returned an identity or list). |
| Do not submit duplicates | If the task’s `报告/` already contains the identical issue (same type on the same URL; changing the ID or adding parameters still counts as the same issue) → do not write another report. Report the same type on a different URL, or a different type on the same URL. Expand the existing report when the same issue is found to have greater impact; do not open a new one. |
| Where to put secrets | Put literal secret values and full JS only in the formal report, not in the short table/knowledge base. |
| Cleanup | When the user asks to clean up: if there is no report, delete the whole task folder; if there is a report, keep only `资产/` and `报告/`. Do not touch accounts/passwords saved in the browser. |
